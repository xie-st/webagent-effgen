# M2 本地故障环境与独立判定

本文件只说明 `02_代码/02_本地测试环境/` 内的 M2 本地交付单元。它不修改 harness、不实现 M2 策略核验/恢复、不引入 M3 浏览器适配器、调度或登录接管，也不产生官方成绩。

## 范围与结论

- 七类既有任务：`profile`、`post`、`reply`、`subscribe`、`vote`、`cart`、`checkout`。
- 新增复合任务：`profile_post`、`reply_subscribe`、`subscribe_vote`、`cart_checkout`，每项至少两个业务要求。
- 故障可按写操作配置、按次数触发、带固定种子；触发记录写入证据。
- 判定器读取实际 Fixture 状态与原任务要求，actor 的 `goal_checks` 只记录、不参与通过判断。
- 写入次数分 `attempt_counts`、`write_counts`、`target` 写入三类；用于未知提交不重发、一次性点赞/订单/回复和精确替换。
- 保留 `start.ps1`、`runner.py`、`smoke_test.py` 原有入口与场景；新增文件均为本目录附加能力。

## 任务与判定

七类任务的要求来自原任务文本，并以 token 生成精确期望：

| 任务 | 业务要求 | 写入规则 |
|---|---|---|
| `profile` | 简介精确等于 `开发者-{token}` | 恰好 1 次目标写入 |
| `post` | 标题精确等于 `并行调度-{token}` | 恰好 1 次目标写入 |
| `reply` | 回复精确等于 `已确认-{token}` | 恰好 1 次目标写入 |
| `subscribe` | 已订阅 | 恰好 1 次提交 |
| `vote` | 点赞数恰好 1 | 恰好 1 次提交 |
| `cart` | 购物车恰好 `["键盘"]` | 恰好 1 次提交 |
| `checkout` | 购物车恰好 `["键盘"]`、订单数 1、已提交 | 购物车与订单各 1 次提交 |

复合任务：

| 任务 | 要求 |
|---|---|
| `profile_post` | 简介 + 帖子标题 |
| `reply_subscribe` | 回复 + 订阅 |
| `subscribe_vote` | 订阅 + 一次点赞 |
| `cart_checkout` | 购物车 + 一次订单 |

判定结果包含每条要求的 `expected`/`actual`、每条写入规则的 `expected`/`actual`、业务快照、故障激活记录。任一要求或写入规则不满足，`passed` 即为 false；复合任务缺一项也不能通过。

`target` 写入规则只统计“提交后实际值达到目标值”的写入。这样：

- 追加故障先产生错误值，再精确修正，只算 1 次目标写入，可以通过最终精确值；
- 未知提交后盲目重发，会产生 2 次目标写入，判定失败；
- 一次性点赞/订单/回复使用业务数量或总写入次数，重复即失败。

## 故障 API

`FaultPlan.from_dict()` / `from_file()` 接受：

```json
{
  "token": "m2-profile-append",
  "seed": {"bio": "旧简介"},
  "faults": {
    "profile": {"mode": "append_value", "times": 1, "note": "demo"}
  }
}
```

字段：

- `token`：可选；固定 Fixture token，便于复现任务文本。
- `seed`：可选；允许 `bio`、`title`、`reply`、`subscribed`、`votes`、`cart`、`ordered`、`orders`。追加故障需要非空旧值才能观察。
- `faults`：按 `profile`/`post`/`reply`/`subscribe`/`vote`/`cart`/`checkout` 配置；也支持 `"*"` 通配。
- `times`：正整数，激活后自动消耗；`FaultPlan.events` 记录每次激活。

四种故障：

| mode | 行为 | 判定效果 |
|---|---|---|
| `no_effect_success` | 返回正常成功重定向，不写状态 | 业务要求与写入次数失败；故障消耗后可恢复 |
| `append_value` | 旧值 + 请求值写回；仅 `profile`/`post`/`reply` | 精确值失败；修正后可恢复 |
| `commit_lost_receipt` | 先提交，再返回 503 和“结果未知”页 | 状态已变；查询确认且不重发才通过 |
| `missing_target` | 返回缺项页，不写状态 | 缺项要求与写入次数失败；复合任务整体不通过 |

`no_effect_success`、`append_value`、`commit_lost_receipt`、`missing_target` 都是本地合成故障，不存在于官方站点。

## 浏览器验收接口

`m2_acceptance.py` 复用 `runner.BrowserAdapter` 的观察/单动作接口，`decide(task, observation, history, action_history, state)` 与现有运行器一致。后续主线程或 M2 worker 可注入真实 Runtime 决策函数，不必改本目录页面或判定器。

脚本套件：

```powershell
.\.venv\Scripts\python.exe m2_acceptance.py --suite scripted
```

套件覆盖正常路径、无效果恢复、追加修正、未知回执（简介/订单）、前缀后局部失败、复合缺项、重复点赞、缺订单，共 10 个场景。`decision_source` 为 `scripted_browser_no_model`，`model_calls` 为 0。

注入真实/外部决策：

```powershell
.\.venv\Scripts\python.exe m2_acceptance.py --task profile `
  --agent 模块:函数 --fault-plan .\m2_fault_plans\profile_unknown.json
```

`--agent` 模式记录 `decision_source=external_agent`、agent 文件 SHA-256、动作日志、实际模型调用元数据和独立判定。它仍是本地合成运行，不是官方成绩；若注入的是脚本驱动，`model_calls` 为 0，不能称为模型验收。

两种模式默认把证据写到项目 `01_文本/05_测试结果/local/<UTC时间>_<标签>/`，不覆盖旧结果；可用 `--out` 指定新的目录。注入决策每步收到同一绝对截止时间与剩余时间；任一步调用量未知时汇总为 null。

```powershell

.\.venv\Scripts\python.exe m2_acceptance.py --suite scripted
```

`.venv` 的 Playwright 需要匹配版本的 Chromium；本次环境已安装 `chromium-1248`，若重建环境后浏览器缺失，运行：

```powershell
.\.venv\Scripts\python.exe -m playwright install chromium
```

## 剩余联调

- 真实 Runtime 联调已由 `m2_runtime_bridge.py` 接入：`--harness-dir` 固定 harness，父进程用本目录 `.venv` 驱动 Chromium，子进程用锁定 EffGen 解释器运行 `Runtime.advance`；确定性 policy 与 AX 核验桩不读 Fixture 真值，独立 grade 写本地结果目录。该联调仍是本地合成检查，不是模型或官方成绩。
- 将本目录的判定器接入 M2 实现前，先固定任务、初态、时限和故障计划，避免把脚本检查当成模型收益。
- 官方评测、真实网站、浏览器接管、调度和多 Tab 不在本单元；不要用本地脚本结果替代官方成绩。
- 本单元证据由主线程登记/归档；本目录不更新开发方案，也不提交推送。
