# 评测与故障诊断

本篇处理清单中的 11、12、33；技能收益评测另见[技能构建与复用](技能构建与复用.md)的 SkillsBench 部分。测试方法用于比较基础 Agent 与增量模块，官方最终判分仍按比赛要求执行。

## 11. StressWeb：把失败分到观察、决策、执行三个环节

**研究思路。** 干净环境中的通过率不能解释 Agent 为什么在真实交互中失效。作者保持任务目标不变，在交互的不同阶段注入扰动，用成对轨迹和检查点定位故障。

**可提取的方法。** 对同一个本地测试任务保存正常版本，再分别加入 DOM 冗余、带说明的交互规则变化、点击未生效、输入未生效、突发弹窗。原文还覆盖视觉布局变化和无提示语义变化；AX 树基线优先取与文本观察、执行回执直接相关的部分。

**项目接入。** 把故障注入器放在自建测试页或本地浏览器适配层，每次只改变一类因素，固定任务、初态和策略版本。给每个关键子目标记录 `expected_predicate / observed_evidence / passed`，形成以下诊断：

| 轨迹表现 | 应优化的模块 |
|---|---|
| 目标元素存在，裁剪后未进入模型输入 | 观察筛选与展开回退 |
| 模型看到了新规则，仍输出旧动作 | 任务约束与行动前检查 |
| 动作已发出，但状态没变，Agent 继续后续步骤 | 执行回执、后置条件与局部修复 |
| 弹窗打断后重复执行已完成写入 | 进度状态与恢复入口 |

每个扰动版记录相对正常版的通过变化、首个未通过检查点、恢复额外动作和重复写入次数。总通过率定位不了错误来源，检查点用于诊断；比赛任务仍是整项通过或不通过。

**代码。** [StressWeb 目录](https://github.com/inclusionAI/AWorld-RL/tree/main/StressWeb)；[ecom_query1.py](https://github.com/inclusionAI/AWorld-RL/blob/main/StressWeb/evaluator/ecom_query1.py) 中 `Evaluator.check_checkpoint_1/2/3()`、`Evaluator.evaluate()` 展示检查点分别求值、最终取全部满足的实现；[批次评估入口](https://github.com/inclusionAI/AWorld-RL/blob/main/StressWeb/evaluator/comprehensive_batch_evaluator.py) 汇总结果。复用检查点组织方式，把其中固定站点的 HTML 规则替换为本任务的可观察谓词。

## 12. ParaGUIBench / ParaGUI：先判断依赖类型，再判断并行收益

**理论。** 并行空间由任务的依赖结构决定。作者区分独立并行、带依赖的并行、纯串行；执行层隔离鼠标与焦点，协调层只传递子任务结果。拆分时必须把上游结果写进下游指令，不能假设 worker 共享规划器的上下文。

**方法。** 规划器每轮下发可独立执行的自包含子任务，接收结构化摘要后再规划。共享对象可划分互不重叠的责任区；真正冲突的写入串行执行。worker 达到自身预算或主动失败时显式返回失败，而不是让主规划器把沉默当完成。

**项目接入。** 真实网站侧将子任务绑定到各自页面；共同修改同一购物车、帖子或账号配置时，依据对象冲突串行提交。每个任务有 `id / depends_on / instruction / output / status`。依赖未通过验证时，下游置为 `BLOCKED`，保留无关分支结果。任务内的 worker 预算由剩余时限设置，论文的固定步数不直接当比赛配置。

**判断优化是否有效。** 论文定义 `L_parallel = Σ轮 max(worker步数)`，步数加速比为 `L_serial / L_parallel`；这不含规划、汇总耗时。项目另记录实际起止时间、模型等待、页面等待与汇总时间。以同一批任务对照串行和并行：先看双方均通过任务的耗时，再看全量通过率和总调用；不要把更多 worker 的总工作量误算为关键路径。

**代码。** [仓库](https://github.com/pkgunboat/ParaGUIBench) 中两类入口有不同用途：

- [contracts.py](https://github.com/pkgunboat/ParaGUIBench/blob/main/src/paraguibench/framework/contracts.py)：`SubtaskSpec`、`ExecutionPlan`、`SubtaskResult`，包含依赖闭合和无环校验，可参考数据结构。
- [scheduler.py](https://github.com/pkgunboat/ParaGUIBench/blob/main/src/paraguibench/framework/scheduler.py)：`DAGScheduler.run()`、`_mark_blocked_dependants()`，参考就绪节点派发与失败阻塞；这是仓库当前通用调度层，按 wave 等待，不等同于 MACU 的持续动态图。
- [parallel_benchmark/](https://github.com/pkgunboat/ParaGUIBench/tree/main/src/parallel_benchmark)：仓库 README 指定的原始论文方法代码入口；通用框架与原始实验实现分开阅读。

自动化平台仍由适配层每次返回一个合法动作；群内答复已确认自动化评测网站不支持多 Tab，多页面并发测试与展示放在真实网站执行器侧。

## 33. ShopGym：从电商约束构造可判定的组合任务

**问题。** 单纯“找到商品”测不到跨页面约束保持、规格选择、购物车修改和中途绕行后的状态保留。作者把任务绑定到店铺的真实目录、集合、可用规格和政策，再检查任务本身是否可完成。

**可提取的方法。** 借用“筛选→排序→检查规格→查看政策→回购物车修改”的组合方式构造测试。筛选条件应来自目标分类自己的商品集合；不能用全站存在某规格推定该分类也支持。生成任务后检查商品归属、规格可用性、目标数量和目标页面，修正有问题的任务时保留任务 ID，只重写被指出的问题项。

**项目接入。** 输入为本地测试店铺目录与用户约束，输出为 `instruction / feasible_targets / success_predicates`。Agent 执行时只见指令与网页；测试器保存目标约束并判定商品、规格、数量及任务要求的终态。测试器掌握的目录数据不注入比赛 Agent。用这组任务检验状态管理与完成检查能否保留全部要求。

**实现参考。** 尚未定位对应公开实现。原文 §2.2.2–2.2.4 给出任务生成和校验逻辑，附录 K 给出校验规则说明，附录 L 给出组合任务提示模板；用于编写自己的测试生成器。原文的任务数据校验器与执行完成判定是两层不同检查。
