# 页面观察与上下文：可接入基础 Agent 的方法

本组覆盖现行清单 07、10、14、15、16、19、20、21。以下“论文机制”还原作者方法，“接入设计”是针对固定 Qwen、可访问性树文本和单请求单动作接口的实现方案。

## 页面观察与信息提取

### 07 Region4Web：用功能区域组织页面，跨步骤只更新变化

**问题与判断。** 点击需要元素粒度，理解页面需要区域粒度。把所有元素平铺给模型，既重复输入，也让模型每步重新推断页面的功能结构。最有价值的是区域化观察与页面内增量更新的结合。

**论文机制。** Region4Web 自底向上把 AXTree 父子边分类为 merge/cut，切分功能区域；每区生成“用途＋当前状态摘要”。PageDigest 在进入页面时按任务选择区域：选中区域提供完整子树，其余只提供用途。页面内以入页快照为参照，删除和修改更新原树，新增节点单独展示；新页面重新分区。另设 `view_all` 观察回退。原版分区器经过训练，语义摘要使用微调小模型。

**接入设计：放在 `decide()` 构造 messages 之前。**

1. 输入当前 AXTree、任务子目标和 `page_digest`。先按现有 landmark、表单、标题与树层级形成区域候选；这是赛题简化方案，不等同论文学习分区器。
2. 新页面由同一个 Qwen 选择相关区域，输出 `region_id → purpose` 与选中集合。当前区保留字段值、标签、提示、完整可操作元素编号；未选区保留目录，允许后续展开。
3. 同页用程序更新增删改。弹窗、错误消息、新表单区优先暴露；URL 改变或结构整体替换时重建。按区域内容 hash 失效摘要，避免每步重新调用模型摘要。
4. 找不到目标或区域证据不足时，本机重新组装完整当前观察交给模型；`view_all` 是本地观察操作，不向官方动作解析器发送虚构动作。

**实现关键。** 原代码依赖稳定 `backendDOMNodeId/bid` 匹配节点；赛方只保证当前元素编号有效。没有稳定 ID 时只能用角色、文本与层级做保守匹配，歧义即刷新区域；输出动作始终绑定本次观察编号。

**代码入口。** [仓库](https://github.com/KWONDU/region4web)；[pipeline/transition.py](https://github.com/KWONDU/region4web/blob/main/pipeline/transition.py) 的 `detect_transitions`；[pipeline/observation_builder.py](https://github.com/KWONDU/region4web/blob/main/pipeline/observation_builder.py) 的 `serialize_digest_observation_minus_removed`。优先抽取差异与渲染逻辑，模型组件另行处理。

### 14 WebChallenger：页面分块、列表分批筛选、内容不变就复用

**问题。** 页面很长时，直接摘要整页容易漏掉目标；长列表又不能一次塞进上下文。作者将页面拆成可独立分析的小块，把难的大调用变成多个有明确范围的小调用。

**论文机制。** `WebsiteMem → PageMem → PageSection → Element` 四层结构承载页面、区块、可操作对象与状态。按 DOM 结构递归切分，重复列表独立处理。观察流水线为：选择区块→区块内提取→合成任务摘要。长列表分批选择相关项；区块摘要和任务提取分别缓存，内容变化才重新提取。论文完整流水线用更多总 token 换取更可靠的决策。

**接入设计。**

- 普通页面沿用基础 Agent；仅在 AXTree 过长、列表候选多或整页决策持续失败时，触发分区处理。输入为任务约束、区块目录、当前列表；输出保留匹配项的原始字段与当前编号，不只返回概括文字。
- 建立 `section_cache[(page_key, content_hash)]` 保存通用摘要；任务提取再加 `task_id/subgoal`，避免把前一任务的答案当作当前提取。切换页面或人工接管后重新校验页面状态。
- 列表按批提取 `selected_items、checked_range、remaining_range`。只有当前排序与任务条件能证明剩余项不可能更优，或所需对象均已得到证据时提前停止。
- 缓存静态导航含义和区块结构；每轮重新取得可操作编号。官方平台侧用 AXTree 层级替代 DOM/截图分块；真实网站侧才接完整 DOM 分块。

**代码入口。** [webchallenger/memory/agent_memory.py](https://github.com/jayoohwang1/webchallenger/blob/master/webchallenger/memory/agent_memory.py) 已核实 `Element`、`PageSection`、`PageMem`、`WebsiteMem`、`EnvMemory` 类；观察与执行主文件为 [webchallenger/agent.py](https://github.com/jayoohwang1/webchallenger/blob/master/webchallenger/agent.py)。先复用数据结构和缓存边界，不必整体迁入离线站点遍历及复合动作。

### 15 Prune4Web：模型只生成筛选参数，程序完成候选评分

**方法。** 作者把“读长 DOM 找目标”拆为规划、过滤、定位。过滤阶段由模型生成 `keyword_weights`，固定评分函数对文本、ARIA 标签、placeholder、其它属性进行分层加权匹配，再给定位器 Top-N 候选。原版默认 N=20，并对规划、过滤和定位模型进行训练。

**接入设计。** 当前子目标明确而 AXTree 很长时，由 Qwen 在规划输出中附带少量关键词、权重与目标角色；本机对当前 AXTree 的 name/value/role 评分，保留候选及其父级标题、相邻标签和状态提示。随后 Qwen 从候选中输出一个合法动作。空候选或多个同名对象时扩大候选集，恢复完整当前观察。自动化平台缺少的 CSS/class 等字段不补造。

这一分工可以复用同一子目标的筛选参数；参数由 JSON schema 校验，评分器为固定代码，无需执行模型生成的任意 Python。关键词过滤用于找控件，任务完成证据、错误提示及用户约束另行保留。

**代码状态。** 未定位到可核查的公开独立实现。论文附录 A.2 说明 `buildDomTree.js`、`isInteractiveElement`、`keyword_weights`、`rapidfuzz` 和 `PorterStemmer` 等实现要素；这些是原文描述，不是本次已取到的代码文件。[论文](https://arxiv.org/html/2511.21398v1)。

### 16 Revisiting Observation Reduction（2605.29397）：按必需信息覆盖率筛压缩器

**理论价值。** 压缩率不能表示观察质量；需要看“删掉后会导致失败的信息”有没有被保留。作者提出近似最小失败集 MFS：从成功轨迹中定位一组观察字段，删除它们会导致失败，进一步缩小后得到局部最小集合。压缩器的 coverage 是完整保留该集合的样本比例。

**接入设计：用于离线选择观察策略。**

1. 保存基础 Agent 的成功轨迹和每步完整 AXTree。先标出动作目标、对象身份、任务条件、字段值和结果提示等候选必要字段。
2. 在可重放的测试环境中删除候选观察字段，比较动作与最终完成情况；按 `ddmin` 缩小失败字段集合。修改模型看到的观察，不修改网页真实数据。
3. 对每个候选压缩规则算 coverage、保留比例及程序耗时；淘汰丢关键字段的方案，再用少量完整任务确认通过率与总耗时。目标保留高 coverage 的低耗时规则，不以压得最短为目标。
4. 选择元素后保留必要结构邻域。原文统一后处理为祖先、最多深度5的后代及前后各3个兄弟；迁移到已有压缩的 AXTree 时从更保守的小邻域开始，保留目标对应标签、列表行和表头。

**代码状态。** 未定位到公开独立实现；原文 §2 给出 MFS/coverage 定义与构造流程，附录 A.6、D 给出后处理和 `ddmin` 细节。[论文](https://arxiv.org/html/2605.29397v1)。

### 20 Read More, Think More：当前观察保真，历史用 diff

**研究判断。** 更多信息能否转成更好动作取决于模型；“一律压缩”与“一律给完整 HTML”都没有普遍优势。最直接可迁移的证据是观察历史能帮助减少重复动作，历史 diff 能减少重复输入。

**接入设计。** 固定 Qwen 和模型配置，当前页保留完整合法 AXTree；历史仅保留近期动作、执行回执与观察增删改。用基础 Agent 对照 `无观察历史 / 最近4步diff / 最近9步diff`，将历史窗口作为可调参数；4和9来自论文实验设置，不视为赛题最优值。每段历史附 step、URL、动作、变化结果；旧编号标记为历史引用，禁止用于当前动作。页面切换时以新页完整观察重建基线，不能只给孤立 diff。输入压缩收益按整任务 token、调用次数和耗时核算。

**代码状态。** 未定位到论文独立公开实现；原文使用 AgentLab、id-based grounding，§3.4 明确比较字符级 diff 与完整观察历史。[论文](https://arxiv.org/html/2604.01535v1)。

## 上下文管理

### 10 PoS / Beyond Memory：维护“目前相信什么、还缺什么”

**理论。** 历史记录告诉模型发生过什么，显式 belief state 才告诉它现在该解决什么。作者维护 `B=(W,G,ΔE,ΔA)`：任务相关世界状态、目标、不知道的信息、尚未完成的状态变化；记录实体、状态、关系及证据来源。状态更新先形成候选，再通过 Belief Sentinel 检查内部冲突和与观察的冲突。

**接入设计。** 在任务内 state 保存 `facts、goal_checks、unknowns、pending_changes、active_gap`。每次收到新观察，先将上一动作意图与真实反馈对齐，再更新有来源的事实；一次点击只表示执行过，不能直接使目标变为已完成。当前决策以一个 active gap 为焦点，保留其余要求，防止只完成部分任务就 stop。页面、账户或对象身份变化时，使依赖旧上下文的事实失效并重新查证。

**无进展恢复。** 原文在一段窗口内联合看“缺口一直未解决、进展停滞、状态反复”，区分 Static、Cycle、Drift，生成恢复约束。赛题版先由程序维护状态签名、重复动作和未完成项，风险触发时让 Qwen 判断：静止则抑制无效状态—动作，循环则打断回路，偏航则重聚焦 active gap；缺信息时要求新证据，缺执行结果时要求任务相关状态变化。恢复期间保持同一 active gap，出现有效进展后解除约束。

**代码入口。** [belief/manager.py](https://github.com/luoyu100/PoS/blob/master/belief/manager.py) 的 `BeliefManager.update/get_context`；[belief/trappingDetection.py](https://github.com/luoyu100/PoS/blob/master/belief/trappingDetection.py) 的 `StableGapIdentityTracker`、`detect_belief_trapping`；[belief/recoveryPlanning.py](https://github.com/luoyu100/PoS/blob/master/belief/recoveryPlanning.py) 的 `compose_recovery_instruction`。原文在非网页执行与诊断任务验证；此处接入设计将其证据源替换为页面观察和动作回执。

### 19 M²：逐步摘要和可检索经验各司其职

**方法。** 内部记忆用逐步短摘要替代旧截图和长推理，每步同时生成动作与摘要，不另设一次摘要调用；外部记忆从成功轨迹提炼可泛化的搜索、导航、验证经验，按任务相似度取少量“防御性提示”。经验必须与当前观察核对后才能使用。

**接入设计。** 本轮优先接内部摘要：Qwen 内部输出 `action、step_summary、state_patch`，适配器只向平台返回 action，摘要和状态留在任务内。摘要写清已观察到的状态、执行过的操作、尚待确认的结果；下一轮收到回执后补上确认结果，防止“准备提交”被概括成“提交成功”。摘要链并非严格常数空间，长任务再按子目标折叠已完成段，关键对象值与完成证据存入结构化账本。

若后续加入经验检索，只从本队合法开发轨迹提炼一般交互规则，记录来源与适用条件；不存最终用例答案。原文的 Top-5、句向量模型和55k轨迹库是作者配置；本赛题先用任务类型与页面语义的本地规则检索，按需提供少量提示，不额外引入未报备辅助模型。

**代码状态。** 未定位到公开实现；§2.2、§2.3、附录 F 给出了记忆更新公式、经验抽取约束和提示结构，可据此编写摘要钩子。[论文](https://arxiv.org/html/2603.00503v1)。

### 21 AgentProg：用程序进度和变量保住跨步骤依赖

**问题与判断。** 重复任务既要忘掉已完成迭代的细节，又不能忘记总任务、待办对象和前序提取值。作者通过显式控制流与数据流，决定哪些历史仍然有用。

**论文机制。** Semantic Task Program 用自然语言步骤加循环、分支、变量表达任务；模型在 Action Generation 与 Program Counter Update 间交替执行。历史组织成执行树，只保留根到当前节点的活动路径；同一程序步骤再次执行时，按 step ID 检索历史结果；关键变量单独持久化。全局 belief 通过 Predict–Verify–Align 发现环境偏离并进入恢复。

**接入设计。** 初始规划输出 `steps、read_vars、write_vars、completion_checks`，任务内保存 `pc、loop_index、vars、processed_keys`。每次只生成当前步骤的一个网页动作；看到完成证据才推进 pc。上下文包含当前路径、活跃变量、当前对象、同 step 最近失败原因；已完成迭代只保留对象键和结果证据。恢复后从未完成对象续做，避免重复提交。对简单线性任务直接用步骤列表，无需先实现完整 DSL；循环与跨页面传值多时再加入执行树。

**代码入口。** [agentprog/plan/workflow_utils.py](https://github.com/MobileLLM/AgentProg/blob/main/agentprog/plan/workflow_utils.py) 已核实 `WorkflowContext`、`WorkflowProgramCounterOperation`、`grab_similar_nodes`、`collect_variables_list`、`summarize_variables`；[agentprog/plan/agentprog_utils.py](https://github.com/MobileLLM/AgentProg/blob/main/agentprog/plan/agentprog_utils.py) 有 `AgentProgContext`、`filter_variables_list`。抽取状态与裁剪结构，动作生成改接官方单动作协议。

## 组合成一个增量改造

| 基础 Agent 的故障或开销 | 接入模块 | 主要参考 |
|---|---|---|
| 重复操作，忘记刚才网页变化 | 当前完整AX树＋历史diff | 20 |
| 把动作执行当成任务成功，遗漏子要求 | 显式目标与证据账本、active gap | 10 |
| 长列表难读，同一静态内容反复提取 | 区域目录、分批筛选、hash缓存 | 07、14 |
| 页面太长，目标控件埋在噪声里 | 参数化评分器＋候选结构邻域 | 15 |
| 裁剪策略难选择 | 必需信息coverage＋整任务耗时 | 16 |
| 历史越跑越长 | 动作同轮摘要，完成段折叠 | 19 |
| 批量对象漏处理或重复处理，跨页值丢失 | pc＋变量＋processed集合 | 21 |

先统一 `TaskState` 里的目标、事实、证据、当前步骤和变量，再让观察压缩器读取同一子目标。Region4Web 与 WebChallenger 是两种区域组织方案，不需要并排运行两套完整观察流水线；M² 的摘要服务于历史，PoS 的账本服务于当前状态，二者不互相替代。
