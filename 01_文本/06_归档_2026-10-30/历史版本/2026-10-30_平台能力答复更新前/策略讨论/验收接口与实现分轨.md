# 验收接口与实现分轨

2026-10-29。依据[验收说明](../比赛要求/结构化资料/05_WebAgent赛题验收说明.md)与[评测平台接入指南](../比赛要求/结构化资料/04_WebAgent评测平台接入指南.md)。

结论先说：**这套验收把任务切成两半，两半的优化目标几乎相反。** 十例自动化用例受接口硬约束，能优化的是"每步选对、少调用、别超时"；一例真实网站用例自由度高，并行、限流、人工接管都在那里体现。把两半混在一起设计，会在自动化用例上白花力气。

## 一、接口的硬事实

来自接入指南，不是推断：

- Agent 在本地跑，客户端主动连评测台，无入站端口。
- 你只实现一个决策函数：`decide(task, observation, history, action_history, state) -> 一个动作`。
- 观察是可访问性树文本 + 元素编号；指南列出的常用动作包括 `click [编号] / type / press / scroll / goto / stop`，完整动作格式以连接包 README 为准。
- **一个请求只返回一个动作**。元素编号必须来自本次观察。
- 模型由平台统一调用（`model.generate(messages)`），**选手不能指定模型或推理参数**，token 与费用由平台结算。
- 整批按固定顺序跑十项，单浏览器，每项限时 300 秒、不限步数，截止后查最终状态。
- 每项开始前重建论坛副本，结束后回收。

## 二、由接口推出的四条结论

**1. 自动化用例的任务内多页面并行能力待核对。** 整批任务串行、一个请求只返回一个动作，并不能证明单个任务不支持多标签页。指南仅列出六种常用动作；是否支持新建、切换标签页及任务内并行，须核对连接包 README 与平台动作解析代码。真实网站用例已明确要求展示多页面并行效果。

**2. 动作批处理这条路被堵死。** 论文里"一次调用完成填表加提交"的语义动作方案，在这个接口下必须拆成逐个动作返回。能省的只有"返回动作之前的那次思考"，不是"返回几个动作"。

**3. 成本口径变了。** 成本 = 调用次数 × 每次 messages 长度。观察是平台给的全量可访问性树文本，所以你每次把它传进模型都在付钱。压缩观察、别塞全量历史、减少无效步数，是三个真正能动的旋钮。

**4. 自驱型框架不能直接用。** Browser Use、Stagehand、Playwright MCP 都自己管浏览器，与"平台给观察、你回动作"的结构不兼容。Playwright 只在真实网站用例——那例是自己起浏览器——才有位置。

## 三、分轨

| | 十例自动化用例 | 一例真实网站用例 |
| --- | --- | --- |
| 谁控浏览器 | 平台 | 你自己 |
| 动作粒度 | 一次一个 | 任意 |
| 可否并行 | 评测任务串行；任务内多页面并行待核对完整协议 | 是（多 tab / 多子任务，评委要看耗时收益） |
| 模型 | 平台统一 Qwen3.6-35B-A3B | 同上，且不得外调 |
| 判定 | 程序化校验器，二值 | 评委现场看 |
| 时间压力 | 每项 300 秒 | 看相对串行的收益 |
| 主攻方向 | 每步动作正确率、观察压缩、失败检测与重试、不浪费步数 | 并行编排、限流节奏、人工接管衔接 |

十例是 60% 门槛和 45% 成功率的全部来源，先做。真实网站用例是演示，等十例稳定后再投入。

## 五、要问赛方的事

1. **电商用例在哪。** 接入指南列的十项全是论坛操作（修改简介、跨版块点赞、回复评论、创建版块、订阅、发帖、回复帖子、踩票、编辑帖子，共九项），且只重建论坛副本；验收说明说"论坛、电商两个网站"。要么指南漏了一项，要么调测台只有论坛、电商只在验收服务器上。这决定自测覆盖面。
2. **模板化轨迹算不算预写死。** 把跑通的十项固化成流程模板，与红线里"预写死任务答案"的边界不清楚。十项固定、站点固定，这个诱惑很大，但踩线的代价是取消成绩。
3. **报告还要不要。** 原题要 3–5 页方案报告并占 10%，验收说明没提。若仍要，内容应重写为"接口约束下的取舍"，而不是原提纲。
4. **并行在自动化用例里怎么体现。** 若验收只看十例通过率，并行只由真实网站用例一票体现，投入比例要重算。
